## 项目目标

项目面向一台信捷 `XD5-60T10-E` PLC 控制的全自动按键组装机。设备通过六工位转盘，将贴片按键的橡胶按键主体和金属钉分步骤组装；经过六个工位后形成一个成品按键。

目标是制作接近实际工厂使用水平的专业生产看板，同时适用于：

- 车间横屏大屏。
- 普通电脑浏览器。
- 现场操作员和生产主管查看。
- 后续远程查看与客户展示。

当前版本只做二维生产看板，不使用 3D 模型。

## 已确认需求

### 显示和视觉

- 主要设计尺寸：`1920 x 1080`。
- 同时适配普通电脑浏览器，已验证 `1366 x 768` 无横向溢出。
- 风格：深灰框架 + 浅色数据区域。
- 状态颜色：
  - 绿色：正常运行。
  - 黄色：等待或警告。
  - 红色：报警。
  - 蓝色：清料过程或普通操作强调。
  - 灰色：停止、离线或未知。
- 颜色不能单独表达状态，必须同时显示图标和文字。
- 主标题：`全自动按键组装机生产看板`。
- 页面显示设备编号：`按键组装机-01`。

### 首页指标

生产总览顶部保留四组指标：

1. 当前批次：完成数量、目标数量、完成率、剩余数量、当前批次不良数。
2. 今日产量：自然日累计成品数量、当前自动批次编号。
3. 生产速度：PLC `HD62` 实际速度及其历史变化。
4. 设备时间：第一版只显示当前状态持续时间，不显示今日累计运行时间和今日累计停机时间。

第一版增加“当前批次不良数”，直接读取 PLC `HD66`。该数值在 `HD40` 产能清零时同步清零，并放在首页“当前批次”指标组内，与完成数量、目标数量、完成率和剩余数量一起展示，不单独占用一张大指标卡。剩余数量按 `HD42 - HD40` 计算，结果小于 0 时显示 0。

### 整机状态

第一版只使用五种整机状态：

- `运行`：PLC `M110 = 1`。
- `清料`：PLC `M48 = 1`，表示清料停机过程。
- `报警`：设备在线时，`M9 = 0`（主安全/驱动条件异常）或 `T100-T128` 中任一可靠报警线圈为 `1`。`M9 = 1` 本身不表示整机报警。
- `停止`：设备在线，但不满足运行、清料或报警条件。
- `离线`：MQTT 数据超过规定时间未更新。

暂不显示“手动模式”和“待机状态”。现有 PLC 中虽有各工位单动、复位及手动动作软元件，但没有找到可靠的整机手动/待机状态信号；瞬时控制动作不能直接当作整机状态。

重新核对触摸屏照片和 PLC 程序后，照片中“产能周期 `9000 UP/H`”是 PLC 根据周期计算出的实际生产速度，对应 `HD62`，不是操作员设置的目标速度。现有 PLC 程序和软元件注释中没有找到独立的目标速度寄存器。第一版只显示 `HD62` 实际速度，不显示人为假设的目标速度和速度达成率；网页不根据 `HD40` 重复计算速度，只保存收到的速度采样，用于速度折线图和历史展示。

首页图表：

- 每小时产量柱状图。
- 实际速度折线图。
- 未来尚未到达的时段必须使用空值，不能画成速度为零，以免被误解为停机。

### 页面结构

当前最终页面为四个：

1. `生产总览`
2. `报警记录`
3. `参数查看`
4. `生产记录`

早期曾计划“工位监控”和六工位实时状态块，后续已明确删除。原因是设备运行时各工位动作变化太快，这些状态对生产看板没有稳定的决策价值。只有工位发生报警时，才在报警信息中显示工位、中文内容和 PLC 代码。

### 报警

- 首页显示当前报警、最近三条报警和今日报警次数。
- 报警页面分为“当前报警”和“历史报警”。
- 历史报警支持按日期、工位和报警代码筛选。
- 报警判定和报警项目以设备现有触摸屏配置为准，不由看板另行筛选或重新定义一套报警。
- 看板沿用触摸屏中的中文报警名称和 PLC 地址/代码，不根据软元件名称自行编造报警文案。
- 报警记录沿用触摸屏主要字段：触发日期、触发时间、计数、内容；内容中保留 PLC 地址/代码，并在能够由现有配置明确判断时补充所属工位。
- PLC `M9` 不是全部报警的汇总位。现场已确认 `M9 = 1` 时仍可存在由 `T100-T128` 表示的气缸报警；结合 PLC 程序，`M9 = 0` 表示主安全/驱动条件异常，具体气缸和真空报警由对应 `T` 线圈判断。
- 触摸屏“报警记录”页面显示的是当前活动报警：报警发生时出现，故障解除后消失，并非永久历史记录。看板如需历史记录，应在网页在线期间根据具体报警位从 `0 -> 1` 的变化自行记录，后续再由 SQLite 持久保存。
- `M211`、`M212` 是工位六不良判定信号，只参与 `HD66` 不良计数，不自行归类为设备故障报警，除非触摸屏现有报警配置确实包含它们。
- 所有报警统一级别，不区分提示、警告和严重故障。
- 报警不播放提示音。
- 历史记录不增加触摸屏未提供的恢复时间和持续时长。
- 发生报警时，首页设备状态和报警区域变红，但不使用持续闪烁动画。

### 参数

参数页面为只读，分为：

- 电机参数。
- 基本参数。
- IO 诊断。

参数名称和原始数值沿用触摸屏文字，不做工程单位换算。IO 同时显示信号名称、PLC 地址、输入/输出类型和接通/断开状态。

触摸屏中的“报警参数”页面当前无具体内容，因此不在第一版中保留空页；检查 PLC 后如存在真实报警参数再增加。

### 生产记录

- 现场无固定白班/夜班结构，按订单随时生产。
- 同一天可能生产多个批次。
- 当前批次目标数量由操作员在触摸屏手动输入。
- 系统自动生成批次编号，例如 `20260806-01`。
- 第一版暂时将 `HD40` 被清零认定为批次切换：清零前的批次结束，清零后开始一个自动编号的新批次。
- 这是在现有 PLC 没有明确订单号、批次号或“新批次开始”变量情况下采用的第一版规则；后续如果 PLC、触摸屏或生产系统提供了明确批次信号，应以明确业务信号替换该规则。
- `HD40` 清零不能同时清掉看板已经累计的“今日产量”；今日产量需要由看板或后续历史数据服务独立保存。
- `HD40` 清零识别采用以下异常保护：网页第一次收到数值时只建立基线，不创建新批次；只有上一有效值大于 `0`，随后连续两次收到 `HD40 = 0`，才确认一次清零；MQTT 断线期间不判断，恢复连接后先等待数据稳定；每次确认的清零事件只创建一个新批次，避免重复创建。
- 当前批次跨过自然日时继续保留，不因日期变化重置；“今日产量”可在新自然日从 0 重新累计。该跨日统计不属于当前设备联通阶段的实施重点。
- 生产记录先显示每日汇总，点击日期后显示当天批次和每小时明细。
- 支持导出标准 `.xlsx` 文件。
- 导出工作簿包含：
  - `每日汇总`
  - `批次记录`
  - `每小时明细`
- Excel 文件由浏览器端 OOXML 生成，使用 `fflate` 压缩，不依赖有已知高危漏洞的旧 `xlsx` 包。

### 历史数据方向（第五阶段已完成）

生产记录长期保存已选择本机 SQLite，而不是只使用浏览器缓存。正式实施时应由 `project2` 本地数据服务持续订阅 EMQX、写入 SQLite，再将实时数据提供给网页；这样浏览器关闭后仍能记录数据。

已选择的保存策略：

- 不保存每秒收到的全部原始报文。
- 批次记录、每小时产量和报警记录保存 1 年。
- 速度曲线按每分钟一个采样值保存 90 天。
- 超期数据自动清理，并支持按日期范围导出 Excel。

第五阶段已在 `project2/server/` 实现本地 Node.js 历史服务，优先使用 Node.js 26 自带的 `node:sqlite`。服务直接通过 MQTT TCP 订阅 `device/esp32-s3/property`，浏览器关闭后仍可记录；网页通过本地 HTTP API 读取历史数据。浏览器保留 MQTT 实时订阅，历史服务不可用时页面显示明确状态，不白屏；网页模拟数据功能已在后续维护中移除。

数据库表为 `metadata`、`batches`、`hourly_production`、`speed_samples`、`alarm_events`。批次/小时产量/报警保存 1 年，速度每分钟一个最后有效值并保存 90 天；启动和定期清理超期数据。`metadata` 持久化历史开始时间、HD40 批次状态、报警边沿和触发计数，服务重启不重复创建批次或报警。

第五阶段统计规则：首条有效报文只建基线；HD40 只累计有效正向增量；上一正值后连续两条 HD40=0 才切换批次；当前批次跨自然日；M9=1 且所有 T=0 不报警，M9 1->0 和 T 0->1 才写触发记录。未核准 T 报警只保留原始代码，不编造中文名称或 PLC 地址。所有日期查询按 `Asia/Shanghai`，数据库时间戳统一为 UTC ISO 格式，分钟桶明确带 `+08:00`。

## 控制与安全边界

第一版是只读看板，不包含任何 PLC 写入操作。

当前明确的实施顺序是先完成设备数据与网页的只读联通，数据稳定后再单独规划和实施控制功能。控制功能不得与本轮 MQTT 只读接入混在一起开发或验收。

用户对后续控制的决定：

- 永远不考虑远程启动机器，风险过高。
- 后期可以评估正常停止、产量清零和部分参数修改。
- 单动模式表示以整个工位为单位执行完整流程或复位。
- 手动模式表示分别控制工位内部气缸、真空、振动等单个动作。
- 单动和手动属于机器控制功能，不属于生产看板展示内容。

未来增加任何控制前必须同时具备：

- 用户身份和权限验证。
- 二次确认。
- 参数上下限。
- 操作日志。
- PLC 安全联锁。
- 对安全停机流程的现场验证。

网页不得直接驱动危险动作，也不得绕过 PLC 联锁。

## 数据链路

计划沿用：

`信捷 XD5-60T10-E PLC -> RS485/Modbus -> ESP32-S3 -> MQTT -> project2`

现有 ESP32 已经能够从这台 PLC 正常读取并上传 10 个电机参数，底层 Modbus 通信已跑通。正式看板要求产量、状态和报警接近一秒更新；原先十秒发布一次的频率不足，需要重新设计快速状态与慢速参数的采样/发布节奏。

第一版目标为所有看板数据统一每 `1` 秒采集并发布一次，包括生产数据、整机状态、报警、电机参数、基本参数和 IO 诊断，不分为快速/慢速两档。真实 PLC 联调时必须确认完整 Modbus 读取和 MQTT 发布能够在一秒周期内稳定完成；如出现读取超时或 PLC/RS485 负担问题，优先优化连续地址批量读取和发布结构，再根据实测调整非核心诊断字段，生产总览核心字段仍以一秒刷新为目标。

通信约定优先兼容旧看板已有格式，减少 ESP32 和网页两端改动：

- MQTT topic：`device/esp32-s3/property`
- JSON 字段结构：`params.<字段>.value`
- 浏览器接入：通过 EMQX MQTT over WebSocket 监听 `8083`，不能直接连接 MQTT TCP `1883`

第一版数据新鲜度规则：

- 连续 `5` 秒没有收到有效 MQTT 数据时，整机状态切换为“离线”。
- 离线期间可以保留最后一次有效数值，但必须明确标记为最后数据，不能显示成仍在实时更新。
- 恢复连接后连续收到 `2` 条有效数据，才恢复为 PLC 所代表的真实整机状态。
- 离线期间不执行 `HD40` 清零和批次切换判断。

现场局域网是第一优先级。后续可以增加互联网远程查看，但不能让现场看板依赖互联网才能运行。开发阶段暂时使用个人电脑，正式生产前应迁移到长期运行的小主机或工控机。

当前阶段只使用本地 EMQX，不使用 OneNET。已确认采用以下测试拓扑：


- ESP32 可以通过 USB 数据线连接本电脑，用于上传程序和查看 `115200` 波特率串口日志。
- 联调时 ESP32 会连接真实机器 PLC，因此最终验证目标是完整链路，而不是脱离 PLC 的单独模拟。

## 修改原则

1. 先保持只读和模拟数据版本可运行，再接真实数据。
2. 不为“看起来高级”增加无法准确计算的 OEE、良率或停机损失。
3. 不恢复六工位快速状态块，除非用户重新明确要求。
4. 不把 HMI 的单动/手动按钮复制到生产总览。
5. 参数、寄存器和 IO 地址必须有 PLC 注释或程序证据。
6. 修改后至少运行 `npm run build`，并检查 1920 和 1366 两种宽度。
7. 不覆盖用户已有 PLC、Excel、PDF 或 XDP 文件。
8. `project2` 的需求结论、实施结果、验证状态和下一步计划应持续更新到本文件；工作区根目录 `AGENTS.md` 只维护跨项目结构和通用规则。
